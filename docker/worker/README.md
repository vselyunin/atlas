# Worker image

`Dockerfile` builds the Atlas Worker image from the repository root:

```bash
docker build -f docker/worker/Dockerfile -t atlas-worker:dev .
```

The build stage installs the workspace with the lockfile, builds `@atlas/contracts` and
`@atlas/worker`, and deploys the Worker with its production dependencies, including a compiled
`node-pty`. The final stage runs that deployment as `node dist/main.js` under the user `atlas`
(UID 1001, home `/home/atlas`). UID 1001 owns the Claude login in the `atlas-agent-home` volume;
changing it means logging in again. The image takes its configuration from the `ATLAS_*`
environment variables and contains no token, host path or login.

Pinned agent tools, installed globally:

| Package                         | Version   | Command  |
| ------------------------------- | --------- | -------- |
| `@anthropic-ai/claude-code`     | `2.1.330` | `claude` |
| `@openai/codex`                 | `0.169.0` | `codex`  |
| `@anthropic-ai/sandbox-runtime` | `0.0.83`  | `srt`    |

Git, bubblewrap, socat and ripgrep come from Debian bookworm. The system Git config sets
`safe.directory = *` because the mounted workspace belongs to the host user.

## Git version and clone flaws

Checked on 2026-11-25 for repository cloning: the image's Git is `2.39.5`, Debian package
`1:2.39.5-0+deb12u3`, which was also the bookworm candidate that day. Debian's changelog
(`apt-get changelog git`; the slim image does not ship it) lists the backported fixes for the known
clone flaws: CVE-2024-32002, CVE-2024-32004, CVE-2024-32020 and CVE-2024-32021 (`deb12u1`),
CVE-2024-50349 and CVE-2024-52006 in the credential protocol (`deb12u2`), and CVE-2025-48384 and
CVE-2025-48385 (`deb12u3`). The image is not affected by those. The Worker's clone also avoids their
triggers: it never recurses into submodules or clones from a local path, builds the address from a
validated `owner/name`, answers credentials only through its own helper for the configured host,
and runs every Git step with hooks off. Rebuilding the image picks up later Debian fixes.

## Seccomp profile

The agent sandbox uses bubblewrap, which needs `clone`, `clone3`, `unshare`, `mount`, `umount2` and
`pivot_root`. Docker's default profile allows these only with `CAP_SYS_ADMIN`, which the container
does not get. Start the container with `--security-opt seccomp=docker/worker/seccomp.json` instead.
`pnpm dev` also passes `--security-opt no-new-privileges` and `--cap-drop ALL`; the sandbox does not
need any capability because bubblewrap in the image is not setuid.

- `seccomp-default.json` is Docker's default profile, with unchanged content and Prettier
  formatting, from
  [`moby/profiles`](https://github.com/moby/profiles/blob/9ee3204f0d0cfa19ca2c6a7b0fcf5a2b353954ae/seccomp/default.json)
  at commit `9ee3204f0d0cfa19ca2c6a7b0fcf5a2b353954ae` (the last commit to touch the file,
  2026-11-10), fetched on 2026-11-22 (UTC). The local Docker Engine was 29.10.0.
- `seccomp.json` is that profile plus one appended rule that allows exactly those six system calls.
  It is generated by `node scripts/seccomp.mjs --write`, not edited by hand.

To update the profile, replace `seccomp-default.json` with the newer default, record its commit
above, then regenerate and check:

```bash
curl -fsSL https://raw.githubusercontent.com/moby/profiles/main/seccomp/default.json \
  -o docker/worker/seccomp-default.json
pnpm exec prettier --write docker/worker/seccomp-default.json
node scripts/seccomp.mjs --write
node scripts/seccomp.mjs --check
```

`apps/worker/tests/seccomp.test.ts` fails when `seccomp.json` differs from the derived profile.

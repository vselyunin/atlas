How Atlas connects to GitHub

Atlas creates its own GitHub App and keeps every credential with the one part of the system that needs it. Three pictures show how: who holds what, how you sign in, and how a repository is cloned.

a request or message a reply or redirect carries a secret
The parts

Only the API holds the App's key

  • The App's key and secret live in .atlas/github-app.json, readable only by you (mode 0600).
  • The App has three permissions (Contents, Pull requests, Metadata), no webhook, and reaches only the repositories you choose.
  • The Board creates the App through GitHub's manifest flow, so no secret is copied by hand.
Sign-in

GitHub says who you are; Atlas decides if you get in

  • First owner. The first sign-in becomes the owner only from the browser that created the App, or after entering the one-time owner code the API prints in its terminal.
  • Members. The owner adds people by GitHub login. They are stored by GitHub ID, so a renamed account keeps its access.
  • Pending sign-ins live in memory. The state in steps 2 and 5 is single-use and tied to a browser cookie. Restarting the API during a sign-in makes it fail with state_invalid; signing in again works.
  • Off switch. ATLAS_AUTH=off disables sign-in and everything that needs GitHub.
Clone from GitHub

The token is made late, used twice and revoked

  • Narrow token. It works for one repository, only for reading contents, and for a short time.
  • Never written down. A 26-line helper script hands the token to Git from an environment variable, so it never appears in a command line, the remote address or .git/config.
  • Git is locked down. User and system configuration are off, hooks are off, redirects are not followed, and only HTTPS is allowed.
  • Recovery. The Worker journals each stage. A clone that never reached cloned shows as "Repository needs attention" and its folder is kept.
Access

Every route says who may call it

One hook in the API enforces the rule each route declares. A route that declares nothing requires a session, so a forgotten declaration fails closed. A test reads the live route list to check them all.

Level Who Examples
public Anyone on this machine Sign-in start and callback, the sign-in state the Board reads on load
session The owner and members Projects, tasks, repository list, links, clones
owner The owner only Adding and removing members
Storage

What is kept where

Place Holds Secret?
App file The App's ID, private key and client secret Yes, mode 0600
SQLite users, auth_sessions, installation, github_links Session IDs and the owner code only as hashes
API memory Pending sign-ins, the clone token while a clone runs Yes, gone on restart
Worker journal Commands and their stages No token, ever
Your browser A session cookie, valid 30 days Yes
Libraries

One new dependency

The pull request adds only @fastify/cookie, the official Fastify plugin for cookies. Everything else uses what the project already had, or Node itself, to keep third-party code away from the credentials.

Need Used Why
Cookies @fastify/cookie (new) Sessions, sign-in state and the setup mark all need cookies
Calling GitHub Node's fetch, checked with zod About a dozen endpoints; tests can point it at a local stand-in
App token (JWT) node:crypto, 16 lines One fixed token shape; no library needed on a security path
IDs, hashes, PKCE node:crypto Built in
Database drizzle-orm on SQLite Already used by the API
Cloning The git program The Worker already runs Git this way, with its own hardening
Board React, TanStack Query Already used by the Board
